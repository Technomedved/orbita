# «Сегодня» и «Завтра» · 0.7.0

## Для пользователя

В навигации рядом с «Сегодня» появился отдельный раздел **«Завтра»**. Дата и часы относятся к выбранному месту, а не обязательно к Windows. После полуночи раздел автоматически показывает следующий календарный день. «Сегодня» остаётся местом текущих действий и общей истории полученных результатов.

В «Завтра» есть:

- **В фокусе завтра**: число событий, напоминаний и связанных проектов; первое событие; следующие шаги проектов с напоминанием на этот день.
- **Погода на завтра**: утро, день, вечер на выбранные часы. Обновление из любого дня получает оба прогноза. Дата и время получения подписаны явно.
- **Лента на завтра**: хронологический план из одноразовых/ежедневных/еженедельных задач, ожидающих повторов и отложенных напоминаний. Можно открыть исходную задачу, проект или уже существующее отложенное уведомление.
- **+ Напоминание**: форма сразу предлагает завтра в 09:00 выбранного места. Дату/время можно изменить; включение остаётся явным действием пользователя.

Это предварительный план. Просмотр не выполняет задачи, не отправляет уведомления, не отмечает дела завершёнными и не начинает учебное занятие. Выключенные задачи в план не входят. Общая пауза показана отдельно и сохраняет своё действие. Настоящие результаты появятся после выполнения в общей ленте/журнале.

Проект без даты автоматически на завтра не назначается. Он попадёт в обзор через своё включённое напоминание или отложенное уведомление. Напоминание, отложенное через полночь, уходит из сегодняшнего фокуса в завтрашний план; исходная запись остаётся в истории. Текст внешней JSON-публикации не анализируется для угадывания даты: фраза «завтра» в тексте сама по себе не создаёт запланированное событие.

При длинном плане сначала выводятся 20 карточек; «Показать ещё» добавляет следующие 20. Это ограничивает число одновременно созданных виджетов, не скрывая общий счётчик. На узком окне навигация идёт в два ряда, на широком — в один.

## Слои и контракт плана

`agenda_service.snapshot(now=None, day_offset=1)` — portable read model версии **1**, без Qt/Win32/сети. Допустимы смещения 0…7; текущий UI использует 1. Читает согласованный снимок SQLite в транзакции, не пишет в неё. `today_service.snapshot()` сохраняет контракт версии 2, дополняется только исключением snooze, назначенного на будущий день, из текущего фокуса.

Результат содержит `date`, IANA `timezone`, `day_offset`, `paused`, полные `counts` (`events`, `reminders`, `projects`), `timeline`, `projects`. Элемент ленты:

```json
{
  "id":"task:task-id:2026-10-19T11:00:00+05:00",
  "source":"task","task_id":"task-id","kind":"reminder",
  "title":"Проверить размеры","body":"Сверить с чертежом",
  "at":"2026-10-19T09:00:00+03:00","state":"scheduled",
  "project_id":null,"task_timezone":"Europe/Moscow"
}
```

`source` — `task` или `snooze`; у snooze есть `event_id`. `state` — `scheduled`, `queued`, `running`, `retry`, `snoozed`. Времена в выдаче приводятся к выбранному месту. `id` стабилен для исходного слота/корня snooze, не является ID нового уведомления. Терминальный уже записанный слот не показывается снова как предстоящий. Повтор с `retry_at` завтра показывается как повтор, даже если первая попытка была сегодня. Проектные элементы дополнительно сверяются с активным проектом и связанной задачей.

`automation_models.occurrences(task,start,end)` вычисляет **все** слоты в полуоткрытом абсолютном интервале `[start,end)`. Каждое расписание использует свой IANA-пояс; границы календарного дня — пояс выбранного места. Поэтому 25-часовой день может содержать два запуска одной ежедневной UTC-задачи. Весенний несуществующий час пропускается; осенний повторяющийся час задачи выбирается один раз (`fold=0`), как в планировщике. Начало существования задачи и `start_at` учитываются.

UI: `TomorrowPage` и общий `WeatherPanel` в `day_ui.py`. Существующие страницы задач/журнала/обучения/проектов сохранили свои индексы и маршруты; завтрашняя страница добавлена отдельно, визуальная навигация сопоставляется с этими маршрутами. `--tomorrow` открывает её в новом экземпляре. Как и прежние CLI-маршруты, при уже работающем единственном экземпляре команда лишь поднимает существующее окно.

UI перестраивает план при изменении данных/минуты/открытии вкладки; неизменный fingerprint не пересоздаёт карточки. Погодные анимации скрытой вкладки/окна остановлены прежним механизмом show/hide.

## Два прогноза и хранение

Схема SQLite остаётся **6**. Новые таблицы и преобразование пользовательских задач не нужны. Перед этапом создана проверенная копия базы и исходников `data/backups/before-tomorrow-070-*`.

`weather_service.build_forecasts()` вызывает поставщика одним запросом, разбивает почасовые данные по двум реальным местным датам. В одной транзакции успеха Engine сохраняет:

- `weather_snapshot`: сегодняшний снимок — прежний ключ сохранён для совместимости;
- `weather_forecasts`: карта `{ISO-дата: snapshot}` ровно на сегодня и завтра, без бесконечного роста.

Snapshot содержит прежние `date`, `fetched`, `hourly`, `location`, `location_key`. Если один из дней отсутствует или ответ неполон, новые данные целиком не фиксируются; предыдущий кэш остаётся. Правила ограниченных повторов, DND и защита от смены места используют существующий Engine. Один результат обновления публикуется с текущей датой и абсолютными датами в заголовке, а не как уже выполненное событие завтрашнего дня.

При отображении выбирается точное совпадение даты **и** location fingerprint. Старый однодневный `weather_snapshot` поддерживается на его исходную дату. Сегодняшний прогноз не выдаётся за завтрашний; при отсутствии нужного дня показываются прочерки и предложение обновить. Устаревание определяется возрастом загрузки (6 часов), а не тем, что прогноз относится к будущему дню. После полуночи вчерашний «завтрашний» кэш можно использовать на его настоящую дату; для нового завтра понадобится обновление.

В [официальном API Open-Meteo](https://open-meteo.com/en/docs) ISO-времена используют фиксированное смещение ответа, которое может не отражать переход DST внутри диапазона. Поэтому запрашиваются Unix timestamps и IANA-пояс места, затем времена преобразуются `zoneinfo`. На краях запроса берётся запас по одному календарному дню; после преобразования остаются только два целевых дня. Это не четыре показываемых прогноза. В редкой получасовой сетке выбирается ближайшая точка в пределах 30 минут, с подписью фактического часа и `≈` на карточке. Более далёкая точка не подменяет отсутствующие данные.

ISO-метки журнала/snooze хранятся с совместимым UTC+5. `reminder_action`/`deliver_snoozes` нормализуют явно переданный aware `now` к этому смещению, чтобы выборки границ дня оставались корректными.

## Проверки

`test_tomorrow.py`: календарные границы, IANA/DST, два запуска в длинном дне, выключенные/терминальные задачи, проекты, snooze через полночь, retry, пассивность просмотра, два кэша, частичный сбой, Unix timestamps, переход суток. `test_tomorrow_ui.py`: навигация/старые маршруты, добавление/редактор, разные даты/температуры, отсутствие подмены сегодняшним прогнозом, скрытая анимация и порции ленты. `verify_tomorrow_release.py`: готовый exe, перезапуск без раннего выполнения, сохранность, последующий единственный запуск и JSON-дедупликация. Все сценарии используют отдельные базы. Живая загрузка двух дней: `data/tomorrow-network-check.json`.

Новых сетевых серверов, почты, ИИ-подключений или мобильных пакетов этот этап не добавляет. Предсказание будущего результата задачи не обещается: раздел показывает существующее расписание и состояние выполнения.
