# Общая поставка и первый запуск · 0.9.0

## Границы продукта

Орбита предназначена для разных пользователей. Город, распорядок автора, данные конкретного ноутбука и рабочие системы не являются настройками продукта. Константа прежнего места остаётся только для чтения старых баз при миграции; прогноз больше не использует её как неявный fallback. Почтовые скрипты — отдельный исторический эксперимент и не входят в пакет. `assistant_app.py` теперь совместимый вход в текущий Qt UI вместо старого Tk-прототипа.

## Начальные данные

`automation_defaults.py` задаёт три стабильных ID: weather, audit, learning-db2. Все выключены. «Отчёт о погоде» предлагает ежедневно 08:00; часы карточек редактируются. Аудит и практика также остаются предложениями, не расписаниями, включёнными за пользователя. Стартовый профиль не содержит событий, запусков, проектов, обучения или местоположения. Db2 — один необязательный установленный курс, не характеристика каждого пользователя.

`preferences_service.py` — portable-сервис первой настройки. Qt-адаптер `onboarding_ui.py` получает системное IANA-имя через QTimeZone; неизвестное имя безопасно заменяется UTC с доступным ручным выбором. При первом создании профиля bootstrap один раз записывает `user_timezone` и выключает topmost. Он может изменить только нетронутые выключенные встроенные шаблоны без запусков; пользовательские задачи не переносит.

`WelcomeDialog` позволяет исправить пояс, выбрать уведомления/анимации и начать без погоды. Закрытие запоминает выбранные значения, при ошибке сохранения сохраняет окно. «Настроить погоду» открывает предварительный просмотр без запроса датчиков. Сетевые запросы и датчики не вызываются открытием welcome. Автозапуск при установке не включается.

Пояс выбранного места имеет приоритет для погоды и списка дней; без места используется `user_timezone`. Это общее правило `app_config.timezone_from_settings`, разделяемое UI и read models. Изменение пояса отображения не меняет существующие напоминания. Встроенные legacy-fallback метки UTC+5 остаются форматом хранения, не геолокацией нового пользователя.

## Обновление 7 → 8

Сначала SQLite backup + integrity_check, затем транзакция. Только задача id=weather с точным прежним названием «Погода для поездок» переименовывается в «Отчёт о погоде». Её id, включение, расписание, config, история и любые другие поля сохраняются. Собственные названия не заменяются. Welcome добавляется только при создании новой базы (`onboarding_pending=true`), существующие базы при обновлении не становятся новыми профилями. Старые согласия, курсы и данные не сбрасываются.

Новый Windows-профиль хранится в `%LOCALAPPDATA%/Orbita`. Если новой базы нет, но уже есть `%LOCALAPPDATA%/UrayAssistant/inbox.sqlite`, выбирается прежняя база без копирования/слияния. Если есть обе — приоритет новой. `AUTOMATION_HOME` остаётся явным override. Windows mutex назван по хешу абсолютного пути профиля, поэтому разные явные профили не перехватывают запуск друг друга. Базы и журналы не пишутся в каталог exe.

## Пакет и документация

`Orbita.spec` использует SPECPATH; `build_desktop.py` собирает именно эту переносимую спецификацию. Никакого зашитого диска проекта в build entry нет. VBS ищет exe относительно самого launcher; исходникам нужен локальный venv или явный ORBITA_PYTHON. Готовый exe включает Python/Qt, ни Codex runtime, ни системный Python ему не требуются.

`release_docs/` — пользовательская документация. `docs/` — документация разработки и передача контекста. `release_layout.py` копирует только явный список публичных документов плюс MANUAL; проверка поставки отвергает SQLite, dpapi, логи, mail.local.json и контекст AGENTS/HANDOFF. Исходный журнал разработки/персональные backup не попадают в дистрибутив. Учебные материалы содержат только вымышленные данные.

Установщика, подписи, автоматического обновления и мобильных клиентов пока нет. Следующий этап установки должен сохранять текущий каталог данных, обновлять зависимости рядом с exe, учитывать запущенный процесс и делать удаление пользовательских данных отдельным явным выбором. Эти возможности не объявляются уже реализованными.

## Проверки

`test_onboarding.py` проверяет чистый профиль, отсутствие скрытого места/сети, смену пояса без переноса задач, отдельные базы, сохранение пользовательского названия/расписания и проверенный backup при миграции. Qt-тесты проверяют полный путь welcome → без погоды → новое напоминание в выбранном поясе, welcome → выбор места без датчиков и ошибку сохранения.

`verify_distribution_release.py` копирует готовый пакет в другой каталог с кириллицей/пробелами, запускает из другого cwd с PATH только System32 и без PYTHONPATH/PYTHONHOME/ORBITA_PYTHON, создаёт два разных LOCALAPPDATA-профиля и проверяет независимость/чистоту, первый экран и JSON-дедупликацию. Это тест на той же Windows 11 с разными окружениями, не два настоящих аккаунта Windows и не чистая виртуальная машина. Другие версии ОС, архитектуры и системные разрешения требуют отдельной проверки перед обещанием поддержки.

## Фактические результаты

Прошли 168 общих проверок, включая 117 проверок ядра. Рабочая база мигрировала 7 → 8 с проверенным backup: изменены только точное стандартное название weather и revision, все остальные поля/таблицы совпали с контрольной копией (`data/neutral-user-migration.json`). Перенесённый пакет успешно запущен в двух пустых окружениях LOCALAPPDATA, без Python в PATH; каталоги с кириллицей и пробелами, другой cwd, отсутствие записей в папку программы и независимость данных проверены (`data/distribution-release-verification.json`).

Визуальная проверка композитора использует отдельные topmost-подложку и панель, проверяет отсутствие перекрытия и цикл выключения/включения закрепления. Это свойство тестового стенда, не изменение стандартного закрепления приложения. Прежний стенд с незакреплённой панелью мог захватить постороннее окно и не является достоверным измерением. Qt-проверки обычного незакреплённого окна остаются в общем наборе.
