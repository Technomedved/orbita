# Данные и миграции

SQLite: `inbox.sqlite`, текущая схема **8** (`PRAGMA user_version`). Каталог выбирается `app_config.data_home()`:

| Среда | Каталог |
|---|---|
| Любая, явный `AUTOMATION_HOME` | Указанный каталог, применяется прежде остальных правил |
| Windows | `%LOCALAPPDATA%/Orbita` для новых профилей; существующая прежняя база UrayAssistant сохраняет свой путь |
| macOS | `~/Library/Application Support/Orbita` — правило реализовано, ОС ещё не проверена |
| Linux | `$XDG_DATA_HOME/orbita` или `~/.local/share/orbita` — правило реализовано, ОС ещё не проверена |

## Семантика, которую нельзя потерять при переносе

- `seen` означает прочтение, `delivered` — уже показанное/погашенное всплытие. Выполнение обработчика, прочтение и действие по напоминанию — разные состояния.
- `action_state`: пусто для обычного результата; `pending`, `snoozed`, `done`, `cancelled` для напоминания. `root_id` связывает цепочку откладываний. После завершения/отмены цепочка не должна воскресать.
- `runs.status`: `queued`, `running`, `retry`, `success`, `failed`, `skipped`, `cancelled`. Ручные слоты имеют префикс `manual-` и отличаются от плановых.
- Стабильные встроенные задачи: `weather`, `audit`, `learning-db2`. Не меняйте ID при переименовании в интерфейсе. UUID проектов, шагов, ссылок и личных задач тоже сохраняются.
- Учебные состояния: `not_started`, `in_progress`, `completed_user`. Последнее — самостоятельная отметка, не SQL-верификация.
- Статусы проекта: `active`, `paused`, `completed`, `archived`. Отметка напоминания не завершает проект/шаг.
- Категория `Демо` скрыта пользовательскими запросами, но записи не удалены. `events()` по-прежнему возвращает полный набор, `user_events()` исключает её до применения LIMIT.

## Расписания и время

`once`: `{"type":"once","at":"2026-10-20T19:30:00+05:00"}`. Повторяемое: `{"type":"daily","time":"19:30","days":[1,3]}`. `weekly` содержит ровно один день. Нумерация Python: понедельник 0, воскресенье 6. Расписание содержит `timezone` — IANA-имя (например, `Europe/Berlin`). `zoneinfo` учитывает DST: отсутствующий час пропускается, повторный осенний выполняется один раз в первом вхождении. ISO-метки журнала нормализуются к прежнему UTC+5 ради совместимости, UI преобразует их в пользовательский пояс. Праздники не моделируются. См. GEOLOCATION.md.

## Безопасное изменение схемы

Обновление 0.9.0 (7 → 8) меняет только стандартное название задачи weather при точном прежнем совпадении; id, включение, schedule, config и история сохранены. Пользовательское название не заменяется. Флаг `onboarding_pending=true` записывается только в новую базу, а не при обновлении старой. Bootstrap UI один раз задаёт новым профилям `user_timezone` и `topmost=false`, оставляя задачи выключенными. Завершение welcome сохраняет уведомления/анимации и снимает pending, не обращаясь к сети/датчикам. Без location_profile пояс берётся из user_timezone; при наличии места используется его пояс.

Обновление 0.8.0 (6 → 7) добавляет индексы `runs_task_latest(task_id,id DESC)`, `runs_day(scheduled_at)`, `events_root(root_id,id)`, `events_action(action_state,created,id)`, `snoozes_due(status,due)`, `snoozes_event(event_id,status)`, `snoozes_root(root_id,status)`. Содержимое таблиц и revision не изменяется. SQLite backup версии 6 проверяется до транзакции; новая база сразу получает схему 7. Настройка `animations` — bool, по умолчанию true; отсутствие ключа совместимо с прежними версиями.

`initialize()` до изменения создаёт SQLite backup в `backups` рядом с базой, проверяет `integrity_check`, затем выполняет изменение транзакционно. Новая схема записывается только после успешной проверки. Более новая неизвестная версия отвергается. Миграция 0.6.0 (5 → 6) добавляет timezone старым расписаниям (Asia/Yekaterinburg), legacy-профиль для старой базы и fingerprint прежнего прогноза; история, ответы, проекты и включение задач сохраняются. Новая база получает пустое место. Настройки геолокации описаны в GEOLOCATION.md.

Перед новой миграцией нужен тест со старой схемой, данными/расписаниями/прогрессом, проверкой сохранения и резервной копии. При восстановлении полностью завершите процесс, отдельно сохраните текущую базу, затем верните выбранную проверенную копию как `inbox.sqlite`. Не копируйте лишь один файл открытой SQLite вместо backup API. Перенос базы между устройствами — ручной перенос, не синхронизация: разрешение конфликтов пока отсутствует.

## Погодные даты и календарный план (0.7.0)

Схема остаётся 6. В settings добавляется при успешном обновлении необязательный `weather_forecasts` — карта двух ISO-дат к снимкам. `weather_snapshot` по-прежнему содержит сегодняшний снимок. Смена дня не меняет дату старого snapshot; отсутствие точного совпадения не подменяется другим прогнозом. `agenda_service` читает tasks/runs/snoozes/projects, не создаёт будущие events. `reminder_action`/`deliver_snoozes` нормализуют переданный aware now к смещению хранения. Подробности: [TOMORROW.md](TOMORROW.md).
