# Запуск, сборка и проверки

## Контрольная среда

Windows 11, Python 3.12.14, PySide6/Qt 6.12.0, PyInstaller 6.22.3, tzdata 2026.5. Зависимости закреплены в `requirements-desktop.txt`. Большая часть прикладного ядра использует только стандартную библиотеку Python; Qt нужен UI.

## Обычная среда разработки

Из корня исходников создайте venv Python 3.12, установите зависимости:

```text
python -m venv .venv
python -m pip install -r requirements-desktop.txt
python orbita_entry.py
```

Перед второй и третьей командами активируйте venv или укажите его Python явно. В Windows это `.venv\Scripts\python.exe`, в macOS/Linux — `.venv/bin/python`. Интернет нужен для первоначальной установки, не для каждого запуска.

На текущем компьютере есть локальные `.ui-runtime`/`.build-tools` и Python из Codex runtime. `run_checks.py` и `build_desktop.py` умеют использовать эти каталоги для Windows/Python 3.12. Они не копируются на другую ОС. Прежний запуск `launch-assistant.vbs` поддерживается; это Windows-обёртка.

## Команды проверки

Для этапа оптимизации: `benchmark_history.py --output data/performance-after-history.json` (200 задач, 60 000 запусков, 20 000 событий); `benchmark_desktop.py --animated --output data/performance-after-animated.json` и без `--animated` для пустого прогноза. `--source <папка исходников baseline>` выбирает старую версию для сравнения тем же инструментом. Запускайте замеры последовательно, отдельно от тестов/сборки, с одинаковым Python/Qt и масштабом. Методика: [PERFORMANCE.md](PERFORMANCE.md).

`verify_performance_release.py` проверяет миграцию заполненной v6-базы и перезапуск через exe во временном каталоге. Бенчмарки не меняют базу пользователя и не обращаются к сети. Регрессионные тесты ограничивают число обращений и виджетов, не требуют конкретного времени на произвольном компьютере.

```text
python run_checks.py --core
python run_checks.py
python verify_window_corners.py --tag after --assert-clear
```

На текущем Windows для прямого запуска Qt-скриптов вне venv может потребоваться `PYTHONPATH=<каталог проекта>/.ui-runtime`. `--core` не создаёт QApplication; общий набор включает UI-тесты. База каждого сценария временная. Сетевые/SMTP-ошибки в тестах моделируются, реальные письма не отправляются. Учебные Db2-запросы не исполняются на SQLite.

Отчёты: `data/checks-core.json`, `data/checks-desktop.json`. Они содержат версию, количество, ошибки, пропуски и длительность. Не приписывайте результатам платформу, на которой их не запускали.

## Сборка desktop

```text
python build_desktop.py
```

Windows-обёртка: `powershell -NoProfile -ExecutionPolicy Bypass -File .\build-desktop.ps1`. Python выбирается из `ORBITA_PYTHON`, локального venv, текущего bundled runtime либо PATH. Имя пользователя в сборщике не зашито.

Сборщик вызывает PyInstaller с переносимой Orbita.spec на активной ОС, затем копирует только публичную справку из release_docs, руководство и сведения о версии в пакет. Windows-результат: `dist/Orbita/Orbita.exe` вместе с `_internal`. В папке также находятся `MANUAL.md`, `docs/START_HERE.md`, `docs/PRIVACY.md`, `README.txt`, `release-manifest.json`. Базу пользователя, резервные копии и почтовые секреты сборщик не копирует.

На текущем Windows после PyInstaller исключается конфликтующая `icuuc.dll`, случайно найденная через Poppler; используется системная ICU. Удаляется только этот конкретный файл внутри результата сборки при наличии системной библиотеки.

Ветви macOS/Linux в сборщике подготовлены, но не проверены на этих ОС. Они не создают пакеты с Windows. Для macOS документация предназначена в `Orbita.app/Contents/Resources/docs`; ещё предстоят реальная сборка и проверка. Android/iOS/TV этим desktop-скриптом не собираются.

## Проверка готового пакета

Полностью завершите основной экземпляр, чтобы диагностические запуски не ограничились восстановлением уже открытого окна. Используйте отдельный `AUTOMATION_HOME` либо проверочные скрипты, которые сами создают временные базы.

- `verify_projects_release.py`: сохранение проекта, плановое напоминание в тихом режиме, перезапуск без дубля, архивирование, JSON CLI.
- `verify_learning_release.py`: сохранение учебного ответа/подсказки, плановые запуски без очереди новых занятий, совместимость CLI.
- `verify_location_release.py`: свежая/v5-база, сохранение данных, отсутствие геолокации без согласия, наличие winrt-плагина и IANA-данных.
- `verify_product_release.py`: режим без демонстрационных элементов, «Сегодня», справка/документы в пакете и smoke без создания событий.
- `Orbita.exe --verify-corners .\data\corners-exe`: настоящие пиксели экрана вне скругления на контролируемой подложке.

`--smoke-test` теперь только кратко запускает/закрывает GUI и не публикует демонстрационную карточку. Это не повод запускать диагностику поверх рабочей базы. `--capture` снимает Qt-окно, а `--verify-corners` дополнительно проверяет эффект Windows — обычный Qt screenshot не ловил исходный дефект.

## Перед выпуском

Проверить данные и резервную копию, выполнить содержательные тесты, осмотреть изменённые экраны в узком/обычном размере, собрать/запустить exe, проверить маршруты и JSON, обновить документацию. После сборки открыть продукт и сообщить ограничения и ссылку на папку. Скрипты `benchmark_desktop.py`/`verify_*` — инструменты разработчика, их кнопок в обычном UI нет.

## Проверка «Завтра» (0.7.0)

`python verify_tomorrow_release.py` проверяет готовый Windows exe во временной базе: просмотр/перезапуск без раннего выполнения, два прогноза, сохранность проекта, последующий единственный запуск и JSON. Отчёт `data/tomorrow-release-verification.json`. `Orbita.exe --tomorrow` открывает новый раздел. Документ TOMORROW.md входит в комплект.

## Общая поставка 0.9.0

`verify_distribution_release.py` копирует настоящий пакет в путь с кириллицей/пробелами, использует другой cwd и свежие LOCALAPPDATA с PATH только System32. Проверяет welcome, пустые профили, выключенные шаблоны, независимость и JSON. Это изоляция окружения на той же Windows 11, не чистая VM/два настоящих аккаунта.

Документация разработки остаётся в docs исходников, пользовательская — в release_docs и docs готового пакета. Список файлов поставки контролирует release_layout.py; ни AGENTS/HANDOFF, ни пользовательские данные в пакет не копируются. Секреты/базы исключены также из VCS. Установщик и подпись пока не реализованы.

## Архивы предварительного выпуска · 0.9.1

`python prepare_licenses.py` скачивает полные исходники используемых Qt/PySide с официальных зеркал, проверяет SHA-256 официального индекса и копирует уведомления в licenses. Полные архивы остаются в data/release-sources. Отключать TLS-проверку нельзя. Уведомления остальных компонентов хранятся в licenses.

Перед релизной сборкой сохраните исходники коммитом. Затем `python build_desktop.py`, проверки exe и `python release_artifacts.py`. Упаковщик откажет при dirty-сборке, несовпадении HEAD или отсутствии/изменении библиотечных исходников. Результаты: dist/releases, SHA256SUMS.txt. Исходные архивы библиотек публикуются рядом с Windows-архивом; не загружайте только exe.

CI в .github/workflows/checks.yml проверяет ядро на Windows; он не собирает и не публикует приложение и не проверяет desktop UI. Полный локальный набор остаётся отдельной проверкой перед выпуском.

## Установщик · 0.9.2

После чистой desktop-сборки: `python build_installer.py`, затем `python verify_installer_release.py` и `python release_artifacts.py`. Нужен Inno Setup 7.1+ (ORBITA_ISCC или .build-tools/inno). Порядок, AppId, изоляция реальной установки и ограничения: [INSTALLER.md](INSTALLER.md).

## Данные · 0.9.3

`test_backup`/`test_data_ui` включены в общий набор. После сборки запустите
`verify_backup_release.py` и `verify_distribution_release.py`. Первый проверяет
нативный UI/CLI и gate; service restore выполняется отдельно от exe, что явно
отражено в отчёте. `verify_installer_release.py` для этого этапа использует
сохранённый настоящий bundle 0.9.2 в data/backups/before-data-093/Orbita.
Новые документы включаются только через release_docs; dev BACKUPS/HANDOFF
не подмешиваются в поставку. Формат архива: [BACKUPS.md](BACKUPS.md).
