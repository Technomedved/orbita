# Подготовка к другим платформам

## Что готово сейчас

Приложение не является одним универсальным бинарником. Подтверждённый продукт — Windows. Уже выделены portable-сервисы и конфигурация без Qt/Win32, общий JSON-совместимый read model, платформенный Windows-адаптер, desktop-сборщик и правила каталогов для Windows/macOS/Linux. Проверка `test_portability.py` блокирует импорты Qt, Windows-адаптера и winreg в отдельном процессе, затем выполняет ядро/проекты/read model. Это проверка зависимостей **на Windows**, не запуск на других ОС.

| Цель | Переиспользование | Что требуется до выпуска | Проверено на устройстве |
|---|---|---|---|
| Windows | Текущая реализация | Текущие проверки/сборка | Да, Windows 11 |
| macOS | Python-сервисы, SQLite, часть Qt Widgets | Нативная упаковка, Dock/меню, разрешения уведомлений, вход в систему, геометрия, подпись/распространение | Нет |
| Linux | Python-сервисы, SQLite, часть Qt Widgets | Нативная упаковка, X11/Wayland, трей/уведомления, автозапуск, системные библиотеки | Нет |
| Android | Модели/состояния/контент/форматы; Python-ядро — после прототипа | Touch UI, сборка ABI, жизненный цикл, локальные уведомления, системное планирование | Нет |
| iOS/iPadOS | Модели/состояния/контент/форматы; Python-ядро — после прототипа | Touch UI, инструменты Apple, подпись, уведомления, жизненный цикл/фон | Нет |
| Android TV | Модели и read model, часть мобильного приложения | Отдельная крупная панель, D-pad, видимый фокус, сценарии без текстового ввода | Нет |

## Стратегия интерфейса

Для desktop сохраняем Qt Widgets и проверяем адаптеры на каждой ОС. Для телефона сначала делаем вертикальный прототип, а не сжимаем существующее окно: список проектов → карточка → сохранение → уведомление → возврат в нужную карточку. Для этого стоит оценить Qt Quick с существующим Python-ядром, а при несоответствии жизненному циклу/упаковке — отдельный UI с теми же форматами и поведенческими тестами. Выбор окончательного мобильного стека ещё не сделан.

Qt for Python уже документирует инструменты [Android и iOS deployment](https://doc.qt.io/qtforpython-6/deployment/index.html), включая [pyside6-ios-deploy](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-ios-deploy.html). Наличие инструментов не означает, что текущая Орбита собрана ими: нам нужны отдельные конфигурации, сборочная среда и проверка конкретного приложения.

Для Android TV обычной адаптации размеров недостаточно. Нужны логичный D-pad-порядок, возврат назад, большой фокус и сокращённые действия; редактирование SQL/длинных заметок не должно быть главным экраном. Эти требования согласуются с [рекомендациями Android TV по навигации](https://developer.android.com/training/tv/get-started/navigation). Текущий desktop-фокус полезен, но не является готовой TV-навигацией.

## Разные модели фоновой работы

Desktop Engine — поток внутри работающего процесса. После закрытия процесса, сна или выключения машины он не выполняет задачи; при запуске восстанавливает состояние. На телефоне нельзя обещать такой же непрерывный поток при остановленном приложении.

Для Android нужно разделить отложенную фоновую работу и действительно точные напоминания, выбрать подходящий системный механизм и проверить необходимые условия/разрешения. В качестве первичных ориентиров: [Task scheduling](https://developer.android.com/develop/background-work/background-tasks/persistent) и [Schedule alarms](https://developer.android.com/develop/background-work/services/alarms). Это будет отдельный адаптер, а не перенос нашего пятисекундного опроса.

В iOS момент фонового обновления выбирает система; нельзя приравнять background refresh к desktop-расписанию на точную минуту. Нужны отдельная стратегия локальных уведомлений и правила обновления данных. Основание: [Apple — Choosing Background Strategies](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app).

## Контракт будущих адаптеров

1. **Пути и жизненный цикл:** каталог приложения, запуск/пауза/завершение, безопасное сохранение перед приостановкой.
2. **Планирование:** регистрировать ближайшее системное событие, принимать wakeup и передавать его прикладному обработчику с назначенным временем/стабильным ID. Сохранять правила пропусков и дубликатов.
3. **Доставка:** сначала записать пользовательский результат, затем запросить показ уведомления ОС. Клик несёт существующий `target`, а не новый серверный URL.
4. **Представление:** не вычислять доменную правильность из состояния виджетов. Для «Сегодня» использовать read model, для редактирования — сервисы/эквивалентные команды.
5. **Хранение:** сохранять схему, ID, корни откладываний и самостоятельный характер учебного прогресса. Если язык/UI меняются, переносить семантику вместе с тестовыми сценариями.

Это описание границы для реализации; универсальный mobile Scheduler API в код ещё не добавлен. Не создаём пустые «готовые» адаптеры для непроверенных платформ.

## Сборка и проверка новой ОС

[PyInstaller собирает под активную ОС и не является кросс-компилятором](https://pyinstaller.org/en/stable/index.html). `build_desktop.py` подготовлен для нативных desktop-запусков; Windows-пакет не станет macOS-пакетом при переименовании. Мобильные пакеты этим скриптом не создаются.

Критерии первого релиза на новой платформе: нативный пакет запускается; прогресс/заметки переживают перезапуск; миграция имеет проверенную копию; пропущенный запуск и snooze не дублируются; тихий режим не останавливает обработчики; клик уведомления открывает правильный объект; корректны клавиатура/touch/D-pad; процессы не теряют данные при реальном жизненном цикле ОС. Сверять нужно реальные устройства/эмуляторы целевой системы.

## Синхронизация отдельно от переноса

Сейчас разные устройства не обмениваются состоянием. Наличие одинаковой схемы SQLite не разрешает конфликты двух копий. Перед будущей синхронизацией нужны владение данными, ID устройства, стратегия конфликта заметок/отметок, отмена напоминаний между устройствами и защита доставки от двойного показа. Сервер или облачную зависимость ради «кроссплатформенности» сейчас не добавляем.

## Геолокация (0.6.0)

Профиль/валидация/IANA-расписания переиспользуются без Qt. Windows-адаптер использует Qt Positioning winrt; прочие ОС — default Qt provider. Для macOS/iOS потребуются usage descriptions/подписи, для Android — manifest/runtime permissions, для Linux — доступный backend. На этих ОС реальных запусков ещё не было. Проверки и правила согласия: [GEOLOCATION.md](GEOLOCATION.md).
