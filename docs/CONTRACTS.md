# Прикладные контракты

## Публикация JSON: существующая совместимость

```json
{"title":"Сборка готова","body":"Можно проверить результат","category":"Проекты","dedupe":"assembly-result-2026-10-17"}
```

Команды: `Orbita.exe --publish-file путь.json` и `python publish.py --file путь.json`. В источнике GUI запускается через `python orbita_entry.py`; прямой запуск CLI не загружает Qt. Кодировка UTF-8, BOM допускается при чтении файла. Обязательны непустые `title`/`body`; `category` по умолчанию «Задачи», `dedupe` необязателен. Повтор того же ненулевого ключа не создаёт второй результат. Остальные поля текущий CLI не использует.

Это локальный файловый интерфейс, **не HTTP API**. Он не исполняет переданный текст как команду/HTML/SQL. Категория `Демо` зарезервирована для старых диагностических событий: такие записи остаются в SQLite, но не показываются как пользовательские.

## Навигационные цели уведомлений

| `target` | Действие |
|---|---|
| `lesson:db2:diagnostic`, `lesson:db2:joins` и другие ID каталога | Открыть конкретное занятие |
| `course:db2` | Открыть обзор обучения |
| `project:<uuid>` | Открыть проект и действия по связанному напоминанию |
| Пусто или неизвестная цель | Показать текст результата |

Существование объекта проверяется сервисом. Это внутренние строковые идентификаторы, не URL для браузера и не команды оболочки. Отложенное событие сохраняет `target` и `root_id`. Старое уведомление открывает указанное в нём занятие, а не молча заменяет его следующим.

## Read model «Сегодня»

`today_service.snapshot(now=None) -> dict` возвращает JSON-совместимый снимок версии **2**. Чтение выполняется в транзакции SQLite, не создаёт задачу, не меняет учебный прогресс и не помечает результат прочитанным.

```json
{
  "version":2,"date":"2026-10-20","timezone":"Asia/Yekaterinburg","paused":false,
  "counts":{"enabled_tasks":0,"active_projects":0,"pending_reminders":0},
  "upcoming":[],"reminders":[],"projects":[]
}
```

`upcoming`: до трёх записей `{task_id,name,at,state}`. Показываются сегодняшние запуски, а также незавершённые ожидающие/просроченные одноразовые запуски с исходным временем. Статусы: `scheduled`, `overdue`, `queued`, `running`, `retry`. Общая пауза отражается отдельно; снимок не обещает запуск в паузе.

`reminders`: до трёх актуальных событий с их полями и `snoozed_until`. Одна цепочка откладывания учитывается один раз, после доставки используется новая запись. `counts` содержит полное число, а не размер сокращённой выдачи. `projects`: до двух активных проектов с `id`, названием, временем изменения и следующим незавершённым шагом. Пауза/архив/завершение проекта исключают его из этого списка.

Модель можно сериализовать для другого интерфейса, но сетевой endpoint сейчас не реализован. Для изменения данных другой интерфейс должен вызывать прикладную команду, не менять этот снимок и не считать его источником истины.

## Основные команды Python

| Область | Команды |
|---|---|
| Задачи | `store.tasks()`, `store.save_task(task)`, `Engine.run_now(task_id)` |
| Напоминания | `store.reminder_action(event_id,'done'/'snooze')` |
| Проекты | `create`, `get`, `save`, `add_step`, `edit_step`, `add_link`, `save_reminder` из `project_service` |
| Обучение | `progress`, `save_progress`, `start`, `complete`, `recommended_order`, `codex_question` из `learning_service` |
| Лента | `store.user_events()`, `store.mark_seen(id)` |
| Техническая история | `store.events()`, `store.runs()` |

Параметры и фактическую валидацию сверяйте с исходниками. Для будущего внешнего API нужны явное версионирование команд, валидация/авторизация и отдельное решение о транспорте; текущие функции сами по себе не являются опубликованным серверным API.

В версии 2 поле `timezone` содержит IANA-имя выбранного места вместо фиксированной строки offset версии 1. Поля JSON-публикации/CLI не изменены. Профиль и weather snapshot: [GEOLOCATION.md](GEOLOCATION.md).
