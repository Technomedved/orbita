# Местоположение и время · 0.6.0

В 0.9.0 новый профиль сначала показывает общий welcome, а не обязательную настройку погоды. Системный часовой пояс берётся из настроек устройства без геолокации, доступен ручной выбор. Без погоды используется user_timezone; с погодой — пояс сохранённого места. «Начать» откладывает погоду без повторного предложения каждый запуск. «Настроить погоду» открывает описанный ниже выбор места без обращения к датчикам. Новая база не использует прежние координаты как fallback. Подробнее: [DISTRIBUTION.md](DISTRIBUTION.md).

## Поведение для пользователя

Раньше координаты Урая и UTC+5 были заданы разработчиком. Геолокация и IP тогда не использовались. В 0.6.0 на первом обычном запуске предлагается выбрать место. Автоматизация геолокации не включается при одной лишь установке или открытии окна.

- **Разрешить и определить местоположение**: одна попытка через службу ОС, затем предварительный просмотр. Сохранение требует кнопки «Сохранить место». ОС сама решает, нужно ли показывать системный запрос разрешения.
- **Найти город**: ручной поиск Open-Meteo; список сохраняет регион/страну и IANA-пояс для одноимённых городов. Запрос идёт по кнопке/Enter, не при каждом символе.
- **Координаты без поиска**: ручное задание координат и IANA-пояса без сетевого поиска. Получение свежего прогноза всё равно требует интернета.
- **Позже / Escape / крестик**: место не меняется, предложение запоминается как просмотренное. Вернуться можно через «Местоположение» на «Сегодня» или настройки.
- Часы трёх погодных карточек настраиваются отдельно. Источник погоды — Open-Meteo; дороги и гололёд не определяются.

При системном определении ОС выдаёт координаты, а не название города. Поэтому начальное имя — «Текущее местоположение»; его можно переименовать перед сохранением. Обратного геокодирования адресов нет. Часовой пояс определяется Open-Meteo по координатам, а не по настройке Windows или IP. Точность ОС показана, когда доступна; её может не хватать для точного попадания в город. При отказе/неточном результате остаётся ручной выбор.

Флажок **«Повторять определение при открытии Орбиты»** по умолчанию выключен, доступен только для системного определения. Он разрешает одну попытку при обычном запуске. Фоновый автозапуск откладывает её до открытия панели. Постоянного отслеживания и фонового доступа к геолокации нет. Ошибка сохраняет последнее место и выводится в панели, без потока одинаковых уведомлений. Ручной выбор отключает этот флажок.

## Данные и приватность

В настройках SQLite хранятся:

| Ключ | Значение |
|---|---|
| `location_profile` | `name`, `latitude`, `longitude`, `timezone`, `source` (`legacy/manual/device`), `accuracy_m`, необязательный `region` |
| `location_setup_complete` | Предложение первого запуска обработано |
| `location_refresh_on_start` | Явное согласие на следующую foreground-попытку |
| `weather_hours` | Три целых часа 0…23 |
| `weather_snapshot` | Прогноз с датой, временем загрузки, `location`, `location_key`, почасовыми данными |

Для device-источника координаты округляются до двух десятичных знаков **до** передачи в Open-Meteo и сохранения. Это сетка примерно до километра, не гарантия точности устройства. Высота, адрес, траектория, Wi-Fi-списки и точные исходные координаты приложением не сохраняются. Ручной поиск передаёт название города в geocoding API. Автоопределение передаёт округлённые координаты в forecast API для часового пояса; погода затем использует сохранённые координаты. Никакого определения по IP и скрытой подмены результатом VPN нет. Сетевой провайдер, как при любом HTTPS-запросе, видит соединение клиента; это не используется нашим кодом как геолокация.

Сохранённое место не является разрешением ОС. Приложение не меняет системные privacy-настройки. В Windows есть кнопка открытия `ms-settings:privacy-location`; доступ для классических приложений регулируется системой. Отказ и недоступность провайдера обрабатываются отдельно от сетевого сбоя.

## Разделение реализации

`location_service.py` — валидация, сохранение, поиск городов, определение пояса, fingerprint. Он не импортирует Qt/Win32 и не читает датчики. Все URL фиксированы на HTTPS Open-Meteo. `location_ui.py` — UI и `DeviceLocator`: `QLocationPermission` approximate/WhenInUse, Qt Positioning, WinRT на Windows. В других системах используется default Qt provider, но сами эти платформы ещё не проверялись.

Геолокация запрашивается в foreground UI-потоке после действия/сохранённого opt-in. Позиционный источник удаляется после результата, ошибки или закрытия. После системного разрешения ожидание координат ограничено таймерами; ожидание ответа самого системного диалога определяется ОС. HTTP выполняется в daemon-потоке с 12-секундным timeout, результат приходит через Qt signal. Поколение запросов и флаг закрытия отбрасывают запоздалый ответ после ручного выбора. Отменённый startup-refresh не сохраняет место.

При изменении места старый прогноз не показывается как относящийся к новому. `Engine._success` сравнивает fingerprint внутри транзакции перед фиксацией погодного результата: устаревший ответ получает `cancelled`, событие и snapshot не публикуются. Пауза/DND по-прежнему используют существующий планировщик и очередь уведомлений. Startup-обновление места не запускает погоду в обход общей паузы; ручной выбор остаётся явным действием пользователя.

## Часовые пояса и совместимость

Каждое расписание содержит IANA `timezone`. При первом выборе места исходные выключенные шаблоны получают этот пояс. Погода следует выбранному месту; существующие напоминания сохраняют свой пояс и точный момент одноразового запуска. Пояс повторяющейся задачи можно изменить явно в её редакторе. В карточке следующий/последний запуск показан во времени выбранного места, строка расписания содержит пояс самой задачи. Проектное напоминание сохраняет пояс своей задачи при повторном редактировании.

`zoneinfo` использует системную IANA-базу или пакет `tzdata`, включённый в Windows-сборку. Несуществующий час весной пропускается в повторении, в одноразовой форме отклоняется. Для повторяющегося осеннего часа выбирается первое вхождение (`fold=0`); второе не создаёт дополнительный слот. Редактор одноразовой задачи тоже выбирает первое вхождение неоднозначного часа. Праздничные календари не реализованы.

Внутренние ISO-метки журнала продолжают использовать прежнее смещение UTC+5, чтобы сохранить SQL-сравнения и ключи слотов. Это формат хранения, а не пользовательский пояс. `parse_time()` возвращает такое нормализованное время; UI должен применять выбранный/задачный пояс. API `new_task()` без явного пояса создаёт UTC-расписание; UI передаёт выбранный пояс. До выбора места панель честно показывает UTC.

Схема **6**: backup API + integrity check перед транзакцией, затем добавление timezone в JSON старых расписаний и legacy-профиля Урая для прежней базы. Старая дата/время и включение задач сохраняются. Старый snapshot помечается legacy-fingerprint. История, SQL-ответы, проекты и прочие настройки не удаляются. Свежая база получает **пустое место**, выключенные задачи и отсутствие согласия на датчики. JSON-публикация/`--publish-file` не менялись. Read model «Сегодня» теперь версии **2**: поле `timezone` — IANA-имя.

## Проверки и границы подтверждения

`test_location.py`, `test_location_ui.py`: города с одинаковым именем, координаты/пояса, сохранение, opt-in, отказы, сеть, запоздалый ответ, midnight/дни недели/DST, резервная копия v5, отсутствие повторного старого слота, гонка при смене места. Новые сценарии не включают реальную геолокацию тестовой машины. `verify_location_release.py` проверяет пакет на свежей и v5-базе, сохранение ответов/проектов/истории и наличие winrt-плагина/IANA-данных. Настоящий position fix после системного разрешения не подменяется тестовым успехом: он требует проверки пользователем кнопкой в готовом приложении. Живые запросы поиска Казани и прогноза проверены отдельно, отчёт `data/location-network-check.json`.
